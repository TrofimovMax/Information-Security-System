# Описание Sequence-диаграммы: жизненный цикл заявки на обучение

## 1. Назначение диаграммы

Sequence-диаграмма описывает полный жизненный цикл заявки на обучение в модуле «Заявки на обучение»: от создания заявки Заявителем до её завершения и перевода в архив.

Диаграмма отражает последовательность взаимодействий между пользователями, Порталом и внешними системами при создании, проверке, согласовании, передаче заявки в СДО, обработке результата обучения и последующей архивации.

На диаграмме должны быть отражены:

* создание заявки через веб-форму;
* добавление списка учеников вручную или через Excel-файл;
* системная валидация заявки;
* сохранение заявки в статусе «Ожидает рассмотрения»;
* рассмотрение заявки Согласующим;
* согласование, отклонение или возврат заявки на доработку;
* повторная отправка заявки после доработки;
* передача согласованной заявки в СДО через API;
* обработка успешного и ошибочного ответа СДО;
* перевод заявки в статусы «Принята», «Завершена» и «Архив».

## 2. Участники Sequence-диаграммы

| Участник                         | Назначение                                                                                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Заявитель**                    | Пользователь, создающий заявку на обучение и отправляющий её на рассмотрение.                                                                        |
| **Согласующий**                  | Пользователь, проверяющий заявку и принимающий решение: согласовать, отклонить или вернуть на доработку.                                             |
| **Портал**                       | Основная система, в которой выполняются создание заявки, проверка данных, смена статусов, отображение уведомлений и интеграция с внешними системами. |
| **БД Портала**                   | Хранилище заявок, статусов, истории изменений, комментариев, данных учеников и результатов обработки.                                                |
| **SSO / Система аутентификации** | Внешняя система, обеспечивающая авторизацию пользователей на Портале.                                                                                |
| **СДО**                          | Внешняя система дистанционного обучения, принимающая согласованные заявки через API и возвращающая результат обработки.                              |
| **Почтовая служба**              | Внешний сервис, используемый для отправки email-уведомлений пользователям.                                                                           |

| 39 | Портал      | Почтовая служба         | Передаёт уведомление о завершении заявки                              | Почтовая служба отправляет email                                                     |

## 4. Альтернативный сценарий: заявка не прошла системную валидацию

|  № | Отправитель | Получатель | Сообщение / действие                                        | Результат                           |
| -: | ----------- | ---------- | ----------------------------------------------------------- | ----------------------------------- |
|  1 | Заявитель   | Портал     | Отправляет заявку на рассмотрение                           | Портал запускает проверку данных    |
|  2 | Портал      | Портал     | Проверяет обязательные поля, формат данных и дубли учеников | Обнаружены ошибки валидации         |
|  3 | Портал      | Заявитель  | Возвращает форму с указанием ошибок                         | Заявитель видит причины ошибки      |
|  4 | Заявитель   | Портал     | Исправляет данные заявки                                    | Данные заявки обновляются           |
|  5 | Заявитель   | Портал     | Повторно отправляет заявку на рассмотрение                  | Портал повторно запускает валидацию |

Рекомендуемый UML-фрагмент:

```plantuml
alt Заявка невалидна
    Портал -> Заявитель: Отобразить ошибки заполнения
    Заявитель -> Портал: Исправить данные заявки
else Заявка валидна
    Портал -> БД Портала: Сохранить заявку со статусом "Ожидает рассмотрения"
end
```

## 5. Альтернативный сценарий: сохранение заявки как черновика

|  № | Отправитель | Получатель | Сообщение / действие                        | Результат                                    |

## 6. Альтернативный сценарий: Согласующий возвращает заявку на доработку

|  № | Отправитель | Получатель      | Сообщение / действие                       | Результат                                      |
| -: | ----------- | --------------- | ------------------------------------------ | ---------------------------------------------- |
|  1 | Согласующий | Портал          | Выбирает действие «Отправить на доработку» | Портал требует комментарий                     |
|  2 | Согласующий | Портал          | Указывает комментарий с причиной возврата  | Комментарий передаётся в Портал                |
|  3 | Портал      | Портал          | Проверяет наличие комментария              | Подтверждается возможность возврата            |
|  4 | Портал      | БД Портала      | Обновляет статус заявки на «На доработке»  | В БД фиксируются статус, комментарий и история |
|  5 | Портал      | Почтовая служба | Передаёт уведомление Заявителю             | Почтовая служба отправляет email               |
|  6 | Портал      | Заявитель       | Отображает уведомление о возврате заявки   | Заявитель видит комментарий Согласующего       |
|  7 | Заявитель   | Портал          | Открывает заявку на доработке              | Портал отображает данные заявки                |
|  8 | Заявитель   | Портал          | Исправляет заявку                          | Портал обновляет данные                        |
|  9 | Заявитель   | Портал          | Повторно отправляет заявку на рассмотрение | Портал запускает валидацию                     |
| 10 | Портал      | БД Портала      | Обновляет статус на «Ожидает рассмотрения» | Заявка снова доступна Согласующему             |

Рекомендуемый UML-фрагмент:

```plantuml
alt Возврат на доработку
    Согласующий -> Портал: Отправить на доработку
    Портал -> Согласующий: Запросить комментарий
    Согласующий -> Портал: Передать комментарий
    Портал -> БД Портала: Статус "На доработке", сохранить комментарий
    Портал -> Заявитель: Уведомить о возврате
    Заявитель -> Портал: Исправить и повторно отправить заявку
    Портал -> БД Портала: Статус "Ожидает рассмотрения"
end
```

## 9. Альтернативный сценарий: ошибка при передаче заявки в СДО

|  № | Отправитель | Получатель      | Сообщение / действие                                | Результат                                           |
| -: | ----------- | --------------- | --------------------------------------------------- | --------------------------------------------------- |
|  1 | Портал      | СДО             | Передаёт согласованную заявку через API             | СДО обрабатывает запрос                             |
|  2 | СДО         | Портал          | Возвращает ошибку обработки или не возвращает ответ | Портал фиксирует неуспешную передачу                |
|  3 | Портал      | Портал          | Проверяет возможность повторной отправки            | Определяется необходимость повторной попытки        |
|  4 | Портал      | СДО             | Повторно отправляет заявку                          | Выполняется повторный запрос                        |
|  5 | Портал      | Портал          | Повторяет отправку до достижения лимита попыток     | Если результат не получен, фиксируется ошибка       |
|  6 | Портал      | БД Портала      | Обновляет статус заявки на «Ошибка СДО»             | В БД фиксируются ошибка, статус и история           |
|  7 | Портал      | Почтовая служба | Передаёт уведомление Согласующему                   | Почтовая служба отправляет email                    |
|  8 | Портал      | Согласующий     | Отображает заявку со статусом «Ошибка СДО»          | Согласующий видит необходимость повторной обработки |

Рекомендуемый UML-фрагмент:

```plantuml
loop Повторная отправка в СДО до лимита попыток
    Портал -> СДО: Передать согласованную заявку
    СДО --> Портал: Ошибка или отсутствие ответа
end

alt Передача в СДО завершилась ошибкой
    Портал -> БД Портала: Статус "Ошибка СДО", сохранить сведения об ошибке
    Портал -> Согласующий: Уведомить о необходимости повторной обработки
else СДО приняло заявку
    Портал -> БД Портала: Статус "Принята"
end
```

## 12. Краткое текстовое описание Sequence-диаграммы

Заявитель авторизуется на Портале через SSO и переходит в модуль «Заявки на обучение». Портал запрашивает в БД список заявок, доступных пользователю, и отображает его. После выбора действия «Создать заявку» Портал формирует форму заявки и при необходимости обращается к СДО для получения актуального списка курсов.

Заявитель заполняет данные заявки, выбирает курс, добавляет список учеников вручную или через Excel-файл, редактирует данные и отправляет заявку на рассмотрение. Портал выполняет валидацию обязательных полей, формата данных и дублей в списке учеников. Если заявка содержит ошибки, Портал возвращает форму Заявителю с указанием причин. Если заявка корректна, Портал сохраняет её в БД со статусом «Ожидает рассмотрения» и уведомляет Согласующего.

Согласующий открывает список доступных заявок, выбирает заявку и просматривает её карточку. Портал проверяет права доступа и контролирует, что Согласующий не является создателем рассматриваемой заявки. После проверки Согласующий принимает решение: согласовать заявку, отклонить её или отправить на доработку.

При возврате на доработку Согласующий указывает обязательный комментарий, Портал меняет статус заявки на «На доработке», сохраняет комментарий и уведомляет Заявителя. Заявитель исправляет заявку и повторно отправляет её на рассмотрение. При отклонении Согласующий также указывает обязательный комментарий, после чего Портал присваивает заявке статус «Отклонена», сохраняет историю решения и уведомляет Заявителя.

При согласовании Портал меняет статус заявки на «Согласована», сохраняет решение в истории и инициирует передачу заявки в СДО через API. Если СДО успешно принимает заявку, Портал присваивает ей статус «Принята». После получения информации о завершении обучения Портал переводит заявку в статус «Завершена».

Если передача заявки в СДО завершается ошибкой или СДО не отвечает, Портал выполняет повторные попытки отправки в пределах установленного лимита. Если передача остаётся неуспешной, Портал фиксирует сведения об ошибке, переводит заявку в статус «Ошибка СДО» и уведомляет Согласующего о необходимости повторной обработки.

После завершения обработки заявка хранится в системе до наступления срока архивирования. По истечении установленного срока Портал переводит заявку в статус «Архив». На этом жизненный цикл заявки завершается.

## 13. Итоговая последовательность статусов заявки

| Этап                                       | Статус заявки            |
| ------------------------------------------ | ------------------------ |
| Сохранение без отправки                    | **Черновик**             |
| Успешная отправка на рассмотрение          | **Ожидает рассмотрения** |
| Возврат Согласующим                        | **На доработке**         |
| Повторная отправка после доработки         | **Ожидает рассмотрения** |
| Отклонение Согласующим                     | **Отклонена**            |
| Согласование Согласующим                   | **Согласована**          |
| Ошибка передачи в СДО                      | **Ошибка СДО**           |
| Успешная передача в СДО                    | **Принята**              |
| Завершение обучения                        | **Завершена**            |
| Истечение срока хранения / перевод в архив | **Архив**                |
